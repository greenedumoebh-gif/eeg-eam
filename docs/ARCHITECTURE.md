# الوثيقة المعمارية — نظام الخدمات المساندة المطور

> منصة ERP/EAM لإدارة دورة حياة الأصول من المناقصة إلى الصرف مجموعة الهندسة الإلكترونية — وزارة التربية
> والتعليم، مملكة البحرين

---

## ١. لماذا هذه المعمارية

النظام السابق بُني على SharePoint + Power Apps + Power Automate. أثبت الفكرة، لكنه اصطدم بأربعة
جدران:

| المشكلة                                                 | أثرها                                                    |
| ------------------------------------------------------- | -------------------------------------------------------- |
| منطق العمل موزّع بين صيغ Power Fx وتدفقات Power Automate | لا يمكن اختباره آلياً؛ كل تعديل مخاطرة                    |
| البيانات في SharePoint Lists                            | حدود العتبة (٥٠٠٠ عنصر)، لا معاملات ذرّية، لا قيود مرجعية |
| لا يوجد تحكم في الإصدارات                               | لا مراجعة كود، لا تراجع عن تغيير خاطئ                    |
| ارتباط كامل بـ Microsoft 365                            | البيانات حيث تقرر Microsoft، لا حيث تقرر الوزارة         |

المعمارية الجديدة تعالج الأربعة: منطق عمل في TypeScript مختبَر آلياً، قاعدة بيانات علائقية حقيقية،
مستودع Git، وحرية كاملة في اختيار مكان البيانات.

## ٢. المبادئ الحاكمة

1. **طبقة بيانات واحدة قابلة للتبديل.** لا استعلام واحد خارج `src/data/`. تبديل مكان التخزين = متغيّر
   بيئة.
2. **منطق العمل في الخدمات لا في الواجهة.** الواجهة الرسومية والـ API كلاهما يستدعيان نفس الدوال في
   `src/services/`. لا ازدواج ولا ثغرة يفتحها مسار دون الآخر.
3. **الحوكمة مفروضة في الكود لا في الإجراءات.** فصل المهام والمطابقة الثلاثية والرقابة على الميزانية
   قواعد تُنفَّذ برمجياً، ولا يمكن تجاوزها بحُسن نية.
4. **صفر تبعيات خارجية في المسار الأساسي.** لا npm، لا JSR، لا CDN. أقل سطح هجوم، وأسرع إقلاع، وأسهل
   تدقيق أمني.
5. **API-First.** كل ما تفعله الواجهة متاح عبر REST، فالربط بأنظمة الوزارة الأخرى لاحقاً لا يحتاج تعديلاً.
6. **عربي RTL أصيل.** ليس ترجمة لواجهة إنجليزية — المصطلحات والرسائل والأخطاء كلها بلغة العمل.

## ٤. السلسلة الأساسية — من العقد إلى الصرف

هذه هي السلسلة التي بُني النظام حولها، وهي مختبَرة آلياً من طرفها إلى طرفها في `tests/chain_test.ts`.

```
① العقد
   يُبرم مع مورد، يحدد: أنواع الأصول المشمولة، المواقع، زمن الاستجابة (SLA)،
   أساس الفوترة (دفعات دورية / لكل أمر عمل)، غرامة التأخير، وبند الميزانية.
   ← لا يُفعَّل عقد بلا بند ميزانية.
                        │
                        ▼
② الأصل
   بنود التوريد تُرحَّل من العقد إلى سجل الأصول بضغطة واحدة، فيولد النظام
   رقم أصل بالبادئة الصحيحة (COP-000001) ويحفظ مرجع العقد داخل الأصل.
   ← تتبّع كامل: من أين جاء هذا الجهاز؟
                        │
                        ▼
③ البلاغ
   يُفتح على «رقم الأصل» حصراً. النظام يشتق النوع والموقع من الأصل نفسه
   (لا إدخال مزدوج)، ثم يبحث آلياً عن العقد الساري الذي يغطي هذا النوع
   في هذا الموقع، فيحدد المورد المسؤول ويحسب موعد الاستجابة من SLA التعاقدي.
   ← عند تداخل التغطية يُختار العقد الأدق (المحدد بالموقع يسبق الشامل).
                        │
                        ▼
④ أمر العمل
   يُفتح على البلاغ، فيخرج الأصل من الخدمة تلقائياً. عند الإنجاز الفني:
     · عقد بدفعات دورية  → underContract=true، لا فوترة منفردة
     · غير ذلك           → مبلغ مستحق قابل للفوترة
     · تجاوز SLA         → غرامة تأخير محسوبة تلقائياً
   ← تسعير أمر العمل صلاحية منفصلة: الفني ينفّذ، والمهندس يسعّر.
                        │
                        ▼
⑤ الفاتورة
   تُبنى من أوامر العمل نفسها — المبلغ محسوب لا مُدخَل. الضريبة ١٠٪،
   والغرامات محسومة. وأمر العمل يُوسَم بمرجع الفاتورة فوراً، فلا يُفوتَر مرتين.
   ← يوجد أيضاً وضع «فوترة آلية» يجمع كل المنجز حسب المورد والعقد.
                        │
                        ▼
⑥ الاعتماد
   لا تدخل الفاتورة المسار قبل نجاح المطابقة الثلاثية:
     ضلع ١: العقد موجود وساري ويعود لنفس المورد
     ضلع ٢: أوامر العمل منجزة بتقارير مكتملة وغير مربوطة بفاتورة أخرى
     ضلع ٣: المبلغ مطابق لمجموع أوامر العمل بعد الغرامات
     + رابع: توفر سيولة في بند الميزانية
   ثم: صانع ← مراجع ← معتمد. ومن تصرّف في خطوة لا يتصرف فيما بعدها.
   ← عند الاعتماد النهائي: حجز المبلغ على بند الميزانية.
                        │
                        ▼
⑦ الصرف
   من غير المعتمد النهائي. يحوّل الحجز إلى صرف فعلي، ويُصدر سند صرف،
   ويقفل الفاتورة نهائياً.
```

كل خطوة في هذه السلسلة تُسجَّل في سجل التدقيق بالفاعل والوقت والتفصيل.

## ٥. نموذج البيانات

```
Supplier ──┬── Contract ──┬── Asset (sourceContractId)
           │              │      │
           │              │      └── Ticket ── WorkOrder ──┐
           │              │                                 │
           │              └── BudgetLine                    │
           │                       ▲                        │
           └────────────── Invoice ┴────────────────────────┘
                             │
                             ├── Approval × 3  (صانع/مراجع/معتمد)
                             └── Payment

AssetType (+ TypeField[])  ← يعرّف الحقول الديناميكية لكل نوع
Site                       ← المواقع والمدارس
User (+ Role[])            ← المستخدمون والأدوار
AuditEntry                 ← سجل غير قابل للحذف
```

### الحقول الديناميكية — أهم قرار تصميمي مُرحَّل من النظام السابق

آلة التصوير لها «سرعة النسخ» و«مزوّد الحبر»، والكاميرا لها «دقة التصوير» و«زاوية الرؤية». بدل إنشاء
جدول لكل نوع، يحمل كل `AssetType` مصفوفة `fields[]` تصف حقوله:

```typescript
{
  key: "resolution",
  label: "دقة التصوير",
  inputType: "قائمة",
  choices: ["720p", "1080p", "2K", "4K"],
  required: true,
  showInGrid: true,
}
```

وتُخزَّن القيم في `asset.attributes` كسجل مفتاح/قيمة. النتيجة:

- **إضافة نوع أصل جديد بحقوله لا تحتاج تعديل كود ولا ترحيل قاعدة بيانات** — سطر واحد في بيانات النوع.
- نموذج الإدخال يُبنى تلقائياً من التعريف، والتحقق من الإلزامية والنوع والقائمة يتم تلقائياً.
- التحويل التلقائي: النص `"42"` يصبح رقماً، و`"true"` يصبح منطقياً.

### لماذا JSONB في PostgreSQL

كل جدول في `schema.sql` له `id` نصي و`data JSONB`، مع فهارس معبَّرة على الحقول المستعلَم عنها كثيراً:

```sql
CREATE INDEX assets_site_idx ON assets ((data->>'siteCode'));
```

هذا يعطي مرونة نموذج KV (نفس شكل السجل في المشغّلين) مع قوة استعلام SQL وفهرسته. وعند نضوج النظام يمكن
ترقية الحقول الحرجة إلى أعمدة حقيقية دون كسر شيء.

## ٦. الأمن والصلاحيات

### الأدوار التسعة

| الدور              | ما يستطيعه                                           |
| ------------------ | ---------------------------------------------------- |
| `admin`            | كل شيء                                               |
| `engineer`         | الأصول، البلاغات، أوامر العمل، **تسعير** أوامر العمل |
| `technician`       | تنفيذ أوامر العمل وإنجازها — **بلا تسعير**           |
| `storekeeper`      | العهد وسجل الأصول                                    |
| `accountant`       | إنشاء الفواتير وتقديمها (صانع)                       |
| `finance_reviewer` | مراجعة الفواتير                                      |
| `finance_approver` | الاعتماد النهائي والصرف                              |
| `supplier`         | بوابة المورد — ما يخصه فقط                           |
| `requester`        | فتح البلاغات ومتابعتها                               |

الصلاحيات مُعرَّفة كقائمة مسمّاة (٢٦ صلاحية) في `src/domain/rbac.ts`، وكل دور خريطة إليها. لا يوجد فحص
صلاحية مكتوب يدوياً داخل منطق العمل — كلها `require_(actor, "invoice:approve")`.

### فصل المهام (Segregation of Duties)

قاعدتان مفروضتان في `src/services/approvals.ts`:

1. من تصرّف في خطوة اعتماد لا يتصرف في خطوة لاحقة على **نفس الفاتورة**.
2. من اعتمد نهائياً لا ينفّذ الصرف.

وهما مختبرتان في `tests/governance_test.ts`. حتى لو مُنح شخص دورين، النظام يمنعه.

### الحماية على مستوى HTTP

- كلمات المرور: PBKDF2-SHA256، ٢١٠٬٠٠٠ تكرار، ملح عشوائي لكل مستخدم، مقارنة بزمن ثابت.
- الجلسات: كوكي `HttpOnly` + `SameSite=Lax` + `Secure`، موقّع بـ HMAC-SHA256، وسجل جلسة في قاعدة
  البيانات يُبطَل عند الخروج.
- CSRF: كل طلب مُغيِّر للحالة يجب أن يأتي من نفس الأصل.
- ترويسات: `Content-Security-Policy`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`.

## ٧. المصادقة — محلية الآن، Entra ID جاهزة

النظام يدعم مسارين للدخول:

**١. الدخول المحلي (مفعّل افتراضياً):** بريد + كلمة مرور، مناسب للتجربة ولمن ليس لديهم حساب في نطاق
الوزارة (كالموردين الخارجيين).

**٢. الدخول الموحّد عبر Microsoft Entra ID (مكتوب ومعطّل):** تنفيذ كامل لـ OpenID Connect بنمط
Authorization Code + PKCE في `src/auth/oidc.ts`. للتفعيل:

```bash
ENTRA_ENABLED=true
ENTRA_TENANT_ID=<معرّف المستأجر>
ENTRA_CLIENT_ID=<معرّف التطبيق>
ENTRA_CLIENT_SECRET=<السر>
ENTRA_REDIRECT_URI=https://<العنوان>/auth/entra/callback
```

**سياسة أمنية مقصودة:** لا يُنشئ الدخول الموحّد مستخدمين تلقائياً. يجب أن يكون البريد مسجّلاً في النظام
بأدواره أولاً، ثم يُطابَق. هذا يمنع أن يحصل أي موظف في الوزارة على وصول لمجرد امتلاكه حساباً.

## ١٠. الترحيل من النظام الحالي

مخططات قوائم SharePoint الحالية مطابقة لنماذج هذا النظام عن قصد. سيناريو الترحيل:

1. تصدير كل قائمة إلى JSON عبر REST API الخاص بـ SharePoint.
2. سكربت تحويل صغير: أسماء الحقول الإنجليزية ← حقول النموذج هنا.
3. الاستيراد عبر `Repo.put()` مباشرة أو عبر REST API.

القوائم المقابلة:

| SharePoint                      | هنا                  |
| ------------------------------- | -------------------- |
| `الأصول`                        | `Asset`              |
| `أنواع الأصول` + `حقول النوع`   | `AssetType.fields[]` |
| `المواقع`                       | `Site`               |
| `الموردون`                      | `Supplier`           |
| `عقود الصيانة` + `تغطية العقود` | `Contract`           |
| `البلاغات`                      | `Ticket`             |
| `أوامر العمل`                   | `WorkOrder`          |
| `الفواتير`                      | `Invoice`            |
| `بنود الميزانية`                | `BudgetLine`         |
| `سجل التدقيق`                   | `AuditEntry`         |

الفرق الجوهري: ما كان يحتاج تدفق Power Automate (الفوترة، التوجيه للمورد، الاعتماد) صار دوالاً في
`src/services/` مختبَرة آلياً.
